# Архитектура Центра познания (Beacon) WATERS v3.1 для 100–500 мобильных нод

**Финальный проект (MVP)**

**Версия документа:** 2.0  
**Дата:** 2026-06-12  
**Автор:** Системный Архитектор WATERS  
**Основание:** ALGORITHMS_OF_UNIVERSE v3.1, ранние прототипы (waters‑node, waters‑node‑v2, waters‑core‑v2), спецификации L0₊, MCP, модели мира LeWM

---

## 1. Общая концепция

Центр познания (Beacon) — это первый узел распределённой сети WATERS. Он обслуживает до **500 мобильных нод**, предоставляя:

- **единое пространство знаний** — слои от галактических аксиом до личных заметок;
- **рынок задач** — общие (от центра) и персональные (от хозяев);
- **групповую работу** — «снежинки» до 6 нод с P2P-обменом и кворумом;
- **интеграцию с роботами** через ROS2;
- **термодинамический регулятор** (\(F_{\text{global}}\), \(\sigma\), \(\beta\), карантин).

Beacon строится на **Rust (axum)**, использует полиглотное хранение (Neo4j, Qdrant, MinIO, PostgreSQL, Redis), упрощённую безопасность (Ed25519 + TLS 1.3) и задел под постквантовую криптографию (фича‑флаг).

---

## 2. Модель данных

### 2.1. Слои знаний (Knowledge Layers)

Иерархический DAG наследования. Каждый слой имеет:

- `layer_id` (UUID),
- `name`,
- `parent_layers`,
- `priority`,
- `scope` (Galactic … Personal),
- `genome_tags`,
- `version` (целое).

### 2.2. Геномы

JSON‑документ в PostgreSQL с полями:

- `genome_id`,
- `parent_genome_id`,
- `name`,
- `layers` (массив ссылок с приоритетами и правами),
- `mutation_allowed`.

Агент получает геном при регистрации; фильтрация знаний при запросе идёт по приоритетам слоёв из генома.

### 2.3. Утверждения (Knowledge Atoms)

Три типа:

1. **Аксиомы** (GDSL‑правила) → Neo4j.
2. **Ситуации** (контекст, действие, результат + латент) → Qdrant.
3. **Эмбеддинги** → Qdrant.

Каждое имеет:
- `layer_id`,
- `confidence`,
- `free_energy_delta`,
- `origin` (MobileAgent / KKZ / Manual),
- `conflicts_with`.

## 3. Физическое хранение (MVP)

| Данные                                      | СУБД               | Причина                                                                 |
|---------------------------------------------|--------------------|-------------------------------------------------------------------------|
| Граф слоёв и аксиом                         | Neo4j              | Язык Cypher, обход наследования                                         |
| Векторы (ситуации, объекты)                 | Qdrant             | ANN‑поиск + фильтрация по layer_id                                      |
| Большие файлы (видео, чекпоинты)            | MinIO              | S3-совместимое, версионирование                                         |
| Реестры, метаданные, геномы, временные ряды | PostgreSQL + TimescaleDB | ACID, JSONB, сжатие временных рядов                                     |
| Кэш, очереди, сессии                       | Redis              | Pub/Sub, TTL                                                            |

На этапе MVP все БД — в Docker‑контейнерах на одном VPS.

```text
│  │ (axum)       │  │ (gRPC)       │  │ (Python,      │  │
│  │ :443 (WSS)   │  │ :9001        │  │  фаза 2)      │  │
│  └──────┬───────┘  └──────┬───────┘  └───────────────┘  │
│         │                 │                              │
│  ┌──────┼─────────────────┼──────────────────────────┐   │
│  │      ▼                 ▼                          │   │
│  │ ┌─────────┐ ┌───────┐ ┌──────┐ ┌─────────────┐   │   │
│  │ │ Neo4j   │ │Qdrant │ │MinIO │ │ PostgreSQL  │   │   │
│  │ │ :7687   │ │ :6333 │ │:9000 │ │ :5432       │   │   │
│  │ └─────────┘ └───────┘ └──────┘ └─────────────┘   │   │
│  │                                                    │   │
│  │ ┌──────┐  ┌──────────────┐                         │   │
│  │ │Redis │  │ TURN/STUN    │                         │   │
│  │ │:6379 │  │ :3478        │                         │   │
│  │ └──────┘  └──────────────┘                         │   │
│  └────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

Rust Beacon – ядро: регистрация, задачи, кворум, обмен весами, метрики, экспорт/импорт слоёв.

ROS2 Bridge – отдельный сервис (gRPC), транслирует команды в ROS2‑топики симулятора.

CUA‑Gym – в фазе 2; в MVP задачи загружаются вручную через `POST /admin/tasks`.

### 4.2. Сетевые протоколы

- Мобильные ноды ↔ Beacon: **WSS (443)**, аутентификация JWT (Ed25519).
- Внутри «снежинки»: **WebRTC Data Channel** (Signal Server на Beacon, TURN для NAT).
- Экспорт/импорт слоёв между центрами: **HTTPS** (прямой JSON).
- **DTN** исключён из MVP (добавляется в фазе 2).

## 5. API (ключевые эндпоинты)

### 5.1. Агенты и задачи

| Метод | Путь                      | Описание                                    |
|-------|---------------------------|---------------------------------------------|
| POST  | `/agent/register`         | Регистрация агента, возврат `agent_id` + `api_key` (JWT) |

| POST  | `/tasks/{id}/claim`       | Взять задачу                                |

### 5.2. Обмен весами LeWM

| POST  | `/weights/upload`   | Загрузить `WorldModelChunk`      |

### 5.4. Геномы и слои

| Метод | Путь                       | Описание                       |

### 5.5. Администрирование (MVP)

| Метод | Путь                 | Описание                                   |

## 6. Геномы и мутации

- Любой агент с флагом `mutation_allowed` может создать дочерний геном через `POST /genome/mutate`.
- Beacon валидирует: проверяет существование слоёв, права, вычисляет приоритеты.
- Конфликты слоёв при наследовании разрешаются по приоритету (больше → главнее).
- Мутации журналируются в `genome_mutations`.

---

## 7. Синхронизация слоёв между центрами (MVP)

Простейший механизм:

- `GET /layers/{id}/export` (JSON до 100 МБ)
- `POST /layers/import`

При импорте сравнивается `version`: если `version_import > version_local`, слой обновляется. Иначе возвращается `409 Conflict`.  
Для больших слоёв (>10k утверждений) предусмотрен HTTP 413 с предложением использовать потоковую передачу (фаза 2).

---

## 8. Безопасность (MVP)

- **Ключи:** Ed25519 генерируются при регистрации ноды; приватный ключ хранится в Android Keystore / iOS Secure Enclave.
- **Канал:** TLS 1.3.
- **Токены:** JWT, подписанный Ed25519, срок 24 ч.
- **Постквантовая защита:** код для ML‑DSA подготовлен, но отключён фича‑флагом. SPIRE Server не используется (сертификаты выпускает сам Beacon).

Этого достаточно для MVP и совместимо с будущим усилением.

---

## 9. Интеграция с ROS2 и эмуляторами роботов

- **ROS2 Bridge** – отдельный сервис на VPS (или рядом), общается с Beacon через gRPC.
- Beacon вызывает `bridge.SendCommand(robot_id, gdsl_action)`, мост преобразует в ROS2‑топик `/robot/command`.
- Сенсорные данные возвращаются через ответ gRPC или поток, упаковываются в `Situation` и сохраняются в Qdrant/Neo4j.
- Поддерживаемые симулятори: **Gazebo**, **Isaac Sim**, **SeeLight S1** (все с ROS2).

## 10. Ресурсы и масштабирование

| Конфигурация         | Минимальные (100 нод) | Рекомендованные (500 нод) |
|----------------------|-----------------------|---------------------------|
| CPU                  | 4 vCPU                | 8 vCPU                    |
| RAM                  | 16 ГБ                 | 64 ГБ                     |
| Диск                 | 250 ГБ NVMe           | 1 ТБ NVMe                 |

- **Ограничения Qdrant:** при 500 нод (~5000 векторов/мин) рекомендуется хранить векторы не дольше 7 дней (TTL).
- **Neo4j:** нагрузка низкая (<10 графовых запросов/с).
- При необходимости масштабирования Qdrant и перехода на JanusGraph — в фазе 2.

## 12. Дорожная карта

- **Фаза 1 (MVP):** один Beacon, ручная загрузка задач, экспорт/импорт слоёв, группы до 6 нод, ROS2 Bridge, Ed25519.
- **Фаза 2:** CUA‑Gym для автогенерации задач, постквантовые подписи (ML‑DSA), SPIRE, DTN для асинхронной доставки, JanusGraph.
- **Фаза 3:** федерация Beacon’ов, глобальный консенсус, эмиссия FFF через смарт‑контракты.

## 13. Учёт ранних прототипов

Из `waters-node` / `waters-node-v2` берём:
- концепцию 8 слоёв взаимодействия,
- Agent ACL,
- Tamagotchi Bootstrap,
- форматы `KnowledgePayload`.

Из `waters-core-v2` берём:
- структуры агента (SDM, Federator, Bongard),
- MCP Store,
- SecurityLearner.

DTN и SPIRE отложены, но соответствующие `trait`’ы заложены в коде для будущей активации.

## 14. LLM, MCP-бриджи и противоречивые знания

- **MCP‑инструменты** (камера, микрофон, `llm_query`, `web_search`) помогают агенту быстро собирать данные.
- **Жёсткое правило:** любые внешние данные проходят Bongard+ (проверка через LeWM).
- **Противоречия** разрешаются через контекстные слои (примеры с помидорами, гамма‑всплеском, фейками) – см. Приложение 14.3.9.

---

## 15. Модель мира LeWM и предсказания

- **LeWM** (JEPA, 15M параметров) работает на мобильной ноде через ONNX.
- **Bongard+** использует предсказанное следующее состояние для верификации.
- Внутренняя награда \(R_{\text{wm}} = \exp(-L_{\text{pred}})\) стимулирует исследование предсказуемых областей (активный вывод, близкий к теории функциональных систем Анохина).
- **Beacon** хранит мастер‑модель (ViT‑H) и выполняет дистилляцию для мобильных нод.
