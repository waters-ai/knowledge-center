# ТЕХНИЧЕСКОЕ ЗАДАНИЕ v3.0 Mobile: «Центр познания + 1000 мобильных нод»

**Версия документа:** 3.0-Mobile-MVP

**Основание:** ALGORITHMS_OF_UNIVERSE v3.1, Agent_OF_UNIVERSE v3.0, WATERS Node v0.6.0, GAP.md, интеграция le-wm и CUA-Gym  
**Статус:** Готово к реализации

## 1. Общее описание системы

Система состоит из одного **Центра познания (Beacon)** и до **1000 мобильных нод** (смартфонов Android/iOS), объединённых в динамические вычислительные кластеры – «Снежинки». Beacon координирует глобальную онтологию (MFTT), рынок задач (с автогенерацией через CUA‑Gym) и термодинамический регулятор. Мобильные ноды собирают сенсорные данные, обучают агентов, выполняют задания, участвуют в кворумах и обмениваются знаниями. Все компоненты используют постквантовую криптографию, DTN‑магистраль и гибридную идентификацию (SPIFFE + DTN EID). На этапе MVP **Kafka исключена** – вся координация через Beacon и прямые P2P‑каналы внутри «Снежинок».

### 2.2. Топология

Система состоит из одного **Центра познания (Beacon)** (VPS) и до **1000 мобильных нод** (Android/iOS). Мобильные ноды могут объединяться в динамические группы («Снежинки») по 2–6 участников для совместного решения задач, обмена латентами и проведения кворума. Из-за отсутствия публичных IP у мобильных устройств все соединения организуются через Beacon, который выполняет роль **сигнального сервера WebRTC** и, при необходимости, **TURN‑ретранслятора**.

   ### Пояснения к цифрам

1. **Постоянные соединения** – каждая мобильная нода поддерживает WebSocket (WSS) к Beacon. По этому каналу передаются: регистрация, получение заданий, отправка решений, обновление метрик, вызов кворума, а также сигнальные сообщения WebRTC (SDP, ICE).

2. **Signal WebSocket** – при создании «Снежинки» ноды обмениваются SDP offer/answer и ICE‑кандидатами через Beacon. Это лёгкие сообщения, нагрузка на Beacon минимальна.

3. **TURN** – если две мобильные ноды не могут установить прямое P2P‑соединение (симметричный NAT, блокировка UDP), они используют TURN‑сервер (развёрнутый на Beacon или на отдельном VPS). TURN ретранслирует DTLS‑пакеты; трафик идёт через сервер.

4. **DTN** – для асинхронной доставки чанков знаний (когда нода временно офлайн) используется DTN‑магистраль. Она может работать поверх WebSocket (store‑and‑forward) или отдельно через libp2p.

5. **WebRTC Data Channel** – после успешного ICE‑согласования ноды устанавливают прямые DTLS‑каналы. Каналы используются для обмена латентами, голосов кворума, чанков весов LeWM, а также для DTN‑трафика. Шифрование — DTLS 1.3.

#### Режимы работы внутри «Снежинки»

- **P2P (режим 1)** – прямое соединение через WebRTC (минимальная задержка, не нагружает Beacon).
- **TURN (режим 2)** – ретрансляция через TURN‑сервер (используется при невозможности P2P).
- **Store‑and‑forward (режим 3)** – асинхронная доставка через DTN (при крайне нестабильной связи).

#### Масштабирование

- Один Beacon (4 vCPU, 8 ГБ RAM) способен обслуживать до 1000 одновременно подключённых мобильных нод и координировать до 500 активных «Снежинок» (групп по 2–6 нод).
- При необходимости TURN‑сервер может быть вынесен на отдельный VPS для разгрузки Beacon.

- **Реестр нод и агентов** – регистрация, хранение AgentId, публичных ключей, репутации Beta(α,β), баланса FFF (заглушка).

- **Beacon Discovery** – статический реестр Beacon’ов (JSON), публичное info‑API.
- **API для мобильных нод** – REST + WebSocket (задачи, решения, загрузка весов, метрики, кворум).

## 4. Мобильная нода

### 4.1. Структура

- **Пользовательские агенты (до 10)** – полноценный когнитивный цикл L0–L4.
- **SDM (Sparse Distributed Memory)** – HNSW‑индекс, ядерная регрессия, Beta‑суперпозиции.
- **LeWM** – инференс через ONNX (`ort` или `candle`), внутренняя награда.
- **Bongard+** – адаптивный порог τ, мягкий вердикт GD/AG.
- **Federator** – двойная награда, адаптивная η (автомат Цетлина), мягкая L1‑регуляризация (Kandel).
- **Прионный протокол** – обмен `WorldModelChunk`, туннелирование, стигмергия.
- **Genome Burst** – сжатие GDSL, дистилляция LeWM, TT‑SVD, фиксация в геноме.
- **Идентификация** – AgentId (UUIDv7), ключи Ed25519 + ML‑DSA, SPIFFE ID (выдаётся Beacon’ом), DTN EID.

### 4.2. Квантовая защита на мобильной ноде

- Гибридные подписи для всех исходящих сообщений.
- Гибридный TLS для HTTPS/WebSocket.
- Ключи хранятся в аппаратном keystore (Android Keystore / iOS Secure Enclave).

## 6. Модель мира LeWM

- **Архитектура** – JEPA (Joint‑Embedding Predictive Architecture), ~15M параметров, предсказание следующего латента.
- **Интеграция** – экспорт в ONNX, инференс на CPU (5–10 FPS).
- **Обучение** – локально (Federator), глобально (федеративное усреднение на Beacon).
- **Использование** – Bongard+ (\(L_{\text{pred}}\)), внутренняя награда \(R_{\text{wm}} = \exp(-L_{\text{pred}})\).

### 7.1. MCP-сервер на ноде

Предоставляет инструменты:

- `audio_record` – запись звука.
- `file_read` / `file_write` – локальное хранилище.

- **Облачный режим** – DeepSeek API или Beacon LLM для сложных задач.
- **Поток:** Агент → MCP Client → MCP-LLM Bridge → LLM.

## 1. Общие требования

Мобильное приложение WATERS реализует функциональность **мобильной ноды** — полноценного узла Вселенной Знаний, способного:

- Запускать до **10 пользовательских агентов**, каждый из которых проходит полный когнитивный цикл **L0–L4** (SDM, Bongard+, Federator, прионный обмен, Genome Burst).
- Взаимодействовать с **Центром познания (Beacon)** через HTTPS/WebSocket и DTN для получения задач, отправки решений, обмена знаниями и участия в кворумах.
- Осуществлять **P2P-взаимодействие внутри «Снежинок»** (групп до 6 нод) через WebRTC (libp2p) и DTN.
- Собирать сенсорные данные (камера, микрофон, файлы), обрабатывать их с помощью модели мира **LeWM** (через ONNX Runtime) и **MCP‑инструментов**.
- Предоставлять пользователю (Хозяину) интуитивный интерфейс для управления агентами, просмотра метрик, участия в групповых миссиях, настройки сети и безопасности.
- Обеспечивать **постквантовую криптографию** (гибридные подписи Ed25519 + ML‑DSA, гибридный TLS) для всех коммуникаций.
- Работать автономно при потере связи (режим **Offline/Hybrid**) с последующей синхронизацией через DTN.
- Поддерживать русский, английский, индонезийский, вьетнамский языки (i18n).

## 3.2. Поток обработки задачи через камеру

1. **Пользователь нажимает «Камера»** на экране агента.
2. **Tauri-плагин захватывает кадр**, передаёт его в `waters-mobile-core` (Rust).
3. **Агент вызывает MCP-инструмент** `camera_capture` → получает изображение `X` (буфер RGB или YUV).
4. **LeWM кодирует `X` в латент** `z` (через ONNX Runtime).
5. **SDM выполняет ядерную регрессию** → предсказание `a` (например, «корова») и начальный `confidence`.
6. **Bongard+ вычисляет ошибку** `L_pred = MSE(pred(z, a), z_next)`. Если `L_pred` ниже адаптивного порога `τ` → решение принято.
7. **Federator обновляет веса** SDM, начисляет FFF (внутренняя и внешняя награда).
8. **При успехе (`confidence > 0.85`)** формируется `WorldModelChunk` (веса LeWM) и отправляется на Beacon через HTTPS или DTN.
9. **Результат (класс, confidence)** возвращается в GUI и отображается пользователю.

## 5. Интеграция с ядром WATERS (L0–L4)

### 5.1. L0 – SDM и LeWM

- **Загрузка модели** – из `assets/lewm.onnx` при старте агента (ONNX Runtime / candle).
- **SDM** – HNSW-индекс в памяти, сериализация в `sdm.bin` при выходе.
- **Суперпозиции** – каждая ситуация хранит `alpha`, `beta` (Beta-распределение) для байесовского обновления.

### 5.2. L1 – Bongard+

- **Физическая верификация** – `L_pred = MSE(pred(z_t, a), z_{t+1}) < τ`.
- **Адаптивный порог** – τ обновляется по метрике ошибок на валидации (локально).
- **Мягкий вердикт GD/AG** – `confidence_proof = 1/(1 + exp(-γ·(ID_proof - θ)))`.
- **Кросс-модальная проверка** – если доступны звук и видео, проверяются обе модальности.

### 5.3. L2 – Federator + Kandel

- **Двойная награда** – \(R = \gamma R_{\text{ext}} + (1-\gamma) R_{\text{wm}}\), \(R_{\text{wm}} = \exp(-L_{\text{pred}})\).
- **Адаптивная η** – автомат Цетлина: `if L_pred > prev_error → η /= 2.0 else η = η * 1.01`.
- **Мягкая L1-регуляризация** (soft-thresholding) для весов SDM.

### 5.4. L3 – Прионный обмен

- **WorldModelChunk** – сериализованные веса энкодера/предиктора LeWM (`PayloadType::Weights`).
- **Публикация** – при confidence > 0.85 чанк отправляется на Beacon.
- **Туннелирование** – при высокой взаимной информации с источником чанк принимается без полного теста (логистическая вероятность).
- **Стигмергия** – веса каналов обновляются по результатам приёма чанков.

### 5.5. L4 – Genome Burst

- **Активация** – после накопления Q новых ситуаций: \(Q \ge Q_{\text{base}} \cdot (1 + \text{ID}/2)\).
- **Сжатие GDSL** – алгоритм Глушкова (поиск минимальной грамматики, покрывающей ситуации).
- **Дистилляция LeWM** – большая модель (ViT-B) → маленькая (ViT-Tiny) с TT-SVD.
- **Фиксация в геноме** – запись в локальный геном и отправка на Beacon.

## 7. Тамагочи – процесс рождения ноды и интерактивный помощник

### 7.1. Тамагочи как Bootstrap (первый запуск)

1. **Приветствие** – анимация, имя пользователя, характер (спокойный/любопытный).
2. **Сбор энтропии** – микрофон, акселерометр, случайные числа → уникальный фрактальный профиль.
3. **Генерация ключей** – Ed25519 + ML-DSA-44. Ключи сохраняются в Secure Enclave.
4. **Запрос SPIFFE ID** – к Beacon через безопасный канал.
5. **Загрузка начального генома** – базовые GDSL-схемы (распознавание простейших объектов, арифметика).
6. **Активация первого агента** – агент «Ученик» с ID=1.0.

### 7.2. Тамагочи как виртуальный ассистент (после рождения)

- **Отображение состояния** – в виде живого персонажа (снежинка, котёнок, робот) на главном экране.
- **Уведомления** – «Твой агент решил сложную задачу! +50 FFF», «Пора запустить Genome Burst».
- **Чат с Тамагочи** – через MCP-инструмент `tamagotchi_chat`, использует локальную LLM.
- **Напоминания** – о прохождении экзаменов, о завершении рейда.

Тамагочи реализован как легковесный агент с собственным ID и ограниченным доступом к API, не влияющий на основные метрики роя.

## 8. Хранение данных и производительность

### 8.1. Локальное хранилище

- **SQLite** (файл `waters.sqlite`):
  - Таблицы: `agents`, `settings`, `situations`, `dtn_queue`, `balance_history`.
- **Файлы**:
  - `sdm.bin` – сериализованный HNSW-индекс и клетки SDM.
  - `lewm.onnx` – веса модели (около 30 МБ).
  - `genome.bin` – локальный геном (сжатые GDSL-схемы).

### 8.2. Память

- **SDM** – до 10 000 клеток, каждая: латент (1280 f32 = 5 КБ) + вес (8 байт) = ~50 МБ. С HNSW-индексом – до 100 МБ на агента. При 10 агентах – до 1 ГБ. В MVP ограничиваем 3–5 агентами или используем сжатие.
- **Модель ONNX** – загружается один раз на всех агентов (общая память) ~30 МБ.

### 8.3. Производительность

- **Инференс LeWM** – в отдельном потоке (Tokio `spawn_blocking`).
- **Поиск в SDM** – не блокирует UI (потокобезопасный HNSW).
- **DTN-очередь** – периодическая синхронизация на фоне.

## 9. Сценарий первого использования

1. **Скачивание** – пользователь устанавливает приложение из магазина (Android/iOS).
2. **Первый запуск** – Тамагочи приветствует, проводит через настройку (имя ноды, характер).
3. **Подключение к Beacon** – при интернете вводится URL (или автоматический discovery). Генерируются ключи, получается SPIFFE ID.
4. **Загрузка начального генома** – агент «Ученик» активирован.
5. **Первая задача** – пользователь нажимает «Камера» и фотографирует корову (или любой объект из домена «Животные»). Агент распознаёт, получает FFF.
6. **Обучение** – после 10–20 задач пользователь видит рост ID и падение F.
7. **Участие в снежинке** – приглашение от другого пользователя или создание группы для совместной задачи.
8. **Сертификация** – после 50 задач агент сдаёт экзамен, получает NFT-диплом (заглушка).

# Техническое задание: Конвейер конвертации знаний (Knowledge Conversion Pipeline) для Центра познания (Beacon)

**Версия:** v1.0-KCP  
**Дата:** 2026-06-02  
**Статус:** Готово к реализации  
**Назначение:** Автоматическое преобразование сырых научных текстов и датасетов (BRIGHT, научные статьи, wiki) в формальные GDSL-схемы, эмбеддинги LeWM и ситуации Поспелова для пополнения глобальной онтологии MFTT.

---

## 1. Общее описание

Конвейер конвертации знаний (ККЗ) — это специализированный компонент Центра познания (Beacon), который реализуется как один из minoda-агентов (расширение Sage) или как самостоятельный сервис, тесно интегрированный с Beacon. ККЗ предназначен для:

- автоматической загрузки сырых текстовых данных (BRIGHT, научные статьи, техническая документация);
- их семантического анализа с использованием больших языковых моделей;
- преобразования извлечённых фактов в формальные GDSL-схемы;
- создания латентных представлений (эмбеддингов) для дообучения модели мира LeWM;
- генерации начальных ситуаций Поспелова для быстрого старта новых агентов.

Конвейер работает исключительно на Beacon (VPS), так как требует значительных вычислительных ресурсов (GPU/CPU) и прямого доступа к глобальной онтологии MFTT. Мобильные ноды получают готовые знания через стандартные API Beacon (рынок задач, глобальные веса).

---

## 2. Входные и выходные данные

### 2.1. Входные данные

- **Датасеты:** BRIGHT (биология, химия, физика, экономика и др.), arXiv, PubMed, Wikipedia, пользовательские загрузки.
- **Форматы:** JSONL, XML, CSV, обычный текст.
- **Структура:** каждая запись содержит `query` (вопрос/тема), `documents` (релевантные статьи), `answer` (опционально), метаданные (домен, источник, дата).
- **Объём:** от десятков мегабайт до сотен гигабайт на датасет.

### 2.2. Выходные данные

- **GDSL-схемы:** формальные правила в синтаксисе GDSL (см. Приложение B документа `ALGORITHMS_OF_UNIVERSE`).
- **Эмбеддинги LeWM:** дообученные веса энкодера и предиктора для конкретного домена.
- **Ситуации Поспелова:** кортежи `(context_latent, action, outcome_latent, confidence)` для записи в MFTT.

---

## 3. Этапы конвейера

### 3.1. Сбор и предобработка

- Загрузка датасетов по URL, через API или из локального хранилища Beacon.
- Очистка текста: удаление HTML-тегов, нормализация Unicode, разбиение на абзацы.
- Фильтрация по языку (ru/en) и домену (согласно конфигурации).
- Сохранение очищенных текстов во временное хранилище (SQLite/файловая система).

### 3.2. Семантический анализ (LLM-экстрактор)

Для каждого фрагмента текста формируется запрос к LLM (DeepSeek-R1, локальный или API) с специализированным промптом. Промпт инструктирует модель извлекать:
- **сущности** (entities): объекты, понятия, явления;
- **отношения** (relations): причинно-следственные связи, атрибуты, иерархии;
- **уверенность** (confidence): оценка достоверности факта (0.0–1.0).

Выход LLM — структурированный JSON.

**Псевдокод:**
```rust
let prompt = format!("Извлеки факты из текста: {text}");
let response = llm_client.query(prompt).await?;
let facts: Vec<ExtractedFact> = serde_json::from_str(&response)?;
```

### 3.3. Генерация GDSL-схем (компилятор в DSL)

Модуль `gdsl_compiler` преобразует извлечённые факты в GDSL-схемы, используя шаблоны:

- `If(And(condition1, condition2), conclusion)` — для причинно-следственных связей.
- `HasProperty(entity, property)` — для атрибутов.
- `BelongsTo(entity, category)` — для иерархий.

**Пример:**  
Факт *"насекомые обладают фототаксисом (движутся к свету)"* →  
`If(And(IsA(X, Insect), LightSource(Y)), MoveTowards(X, Y))`

Сгенерированные схемы проходят синтаксическую проверку GDSL-парсером.

### 3.4. Верификация через GD/AG

- Каждая новая GDSL-схема проверяется на непротиворечивость с существующей онтологией MFTT.
- Используется упрощённый GD/AG-прувер (секвенциальное исчисление без сечения).
- Если схема конфликтует с уже известными аксиомами, она помечается как *"требует ручного разрешения"* (эскалация к Sage/Хозяину).

### 3.5. Создание эмбеддингов LeWM

- Тексты статей кодируются в латентные векторы \(z\) с помощью текущей модели LeWM.
- Дообучение предиктора LeWM: на основе извлечённых причинно-следственных пар модель учится предсказывать латент \(z_{\text{next}}\) для заданного \(z_t\) и действия \(a\) (действие = *"применить правило"*).
- Используется few-shot fine-tuning с замороженным энкодером (чтобы не разрушить общие знания).
- **Результат:** доменно-специфичные веса предиктора.

### 3.6. Формирование ситуаций Поспелова

Для каждой верифицированной GDSL-схемы создаются эталонные ситуации:
- `context_latent`: латентный вектор текста до применения правила.
- `action`: GDSL-схема.
- `outcome_latent`: латент после применения.
- `confidence`: на основе уверенности LLM и GD/AG-верификации.

Ситуации записываются в MFTT как начальные знания для новых агентов соответствующего домена.

### 3.7. Публикация в MFTT и обновление глобальных весов

- GDSL-схемы через CRDT-слияние добавляются в онтологию MFTT.
- Дообученные веса LeWM отправляются в общий пул весов Beacon.
- При следующем Genome Burst они усредняются с другими доменными весами и становятся частью глобального генома.
- Beacon логирует все изменения; статистика доступна через `/metrics/global`.

## 5. Интеграция с существующей архитектурой WATERS

### 5.1. Beacon API

- `POST /knowledge/import` — загрузка датасета Хозяином (опционально).
- `GET /knowledge/status` — статус текущих задач конвертации.
- `GET /knowledge/domains` — список доменов с количеством GDSL-схем.

### 5.2. Minoda-агенты

- **Sage** управляет приоритетами: выбирает, какие домены конвертировать в первую очередь, на основе востребованности задач на рынке.
- **Librarian** проверяет топологическую целостность MFTT после добавления новых схем (TopID).
- **Archivist** создаёт резервные копии до и после массового импорта.

### 5.3. Genome Burst (L4)

- При накоплении значительного объёма новых весов LeWM Beacon запускает федеративное усреднение и дистилляцию.
- Обновлённый геном (GDSL + LeWM) рассылается мобильным нодам.

### 5.4. Экономика FFF (перспектива)

- Хозяева, загрузившие качественные датасеты, могут получать FFF за вклад в глобальную онтологию.
- Валидность вклада оценивается Beacon через сравнение качества новых схем с эталонными задачами.

## 6. Требования к ресурсам

- **CPU:** 8–16 vCPUs.
- **RAM:** 32 ГБ (для LLM-инференса при использовании локальной модели).
- **GPU:** опционально, но рекомендуется (NVIDIA RTX 4090/A100) для ускорения LLM и дообучения LeWM.
- **Диск:** 500 ГБ NVMe SSD (хранение датасетов, кэша, моделей).
- **Сеть:** статический IP, порты 443/80, доступ к LLM API (если не локальный).

# План интеграции le-wm в WATERS MVP: Центр познания и Мобильные ноды

**Дата:** 2026-06-02  
**Статус:** Детальный план работ, основанный на анализе репозитория le-wm

---

## 1. Общая архитектура использования le-wm

Модель мира LeWM (JEPA) становится когнитивным ядром всей системы, но распределяется асимметрично:

- **Beacon (Центр познания)** — владелец мастер-модели (ViT-H/14, ~632M параметров). Выполняет обучение, дообучение, дистилляцию и хранение чекпоинтов.
- **Мобильные ноды** — используют облегчённую версию (ViT-S/16, ~15M параметров), экспортированную в ONNX. Выполняют только инференс и лёгкое дообучение (Federator).

---

## 2. Что разрабатывается на Beacon (Недели 1–8 MVP)

### 2.1. Мастер-модель LeWM

**Задача:** Развернуть на Beacon полную версию le-wm (ViT-H/14) для обучения и дистилляции.

**Компоненты:**

- `lewn_master` — крейт/модуль, загружающий предобученные веса (из репозитория le-wm или Hugging Face) и предоставляющий API для инференса и дообучения.
- **Хранилище чекпоинтов:** SQLite + файловая система. Beacon хранит все версии мастер-модели и дистиллированные варианты.
- **Fine-Tuning Pipeline:** на 11+ неделе подключается ККЗ, который будет дообучать мастер-модель на датасетах (BRIGHT). На этапе MVP (1–8) закладываем `trait LeWMFineTuner` с пустой реализацией.
- **Дистилляция:** модуль `distiller` (часть Genome Burst), который сжимает ViT-H → ViT-S с помощью teacher-student обучения.

### 2.2. Управление весами и федеративное усреднение

**Задача:** Beacon агрегирует веса, полученные от мобильных нод, и выполняет федеративное усреднение.

**Компоненты:**

- **Пул весов:** принимает `WorldModelChunk` от нод, сохраняет в таблицу `weights_pool` (SQLite) с полями: source (MobileNode/KKZ), domain, loss, timestamp.
- **Федеративное усреднение (FedAvg):** раз в сутки или при накоплении N чанков Beacon вычисляет средневзвешенные веса и обновляет глобальную модель.
- **Рассылка:** `GET /weights/global` — возвращает актуальные веса для нод.

### 2.3. Репозиторий предобученных скиллов

**Задача:** Beacon хранит и раздаёт агентам готовые чекпоинты под разные специализации.

**Компоненты:**

- **Каталог скиллов:** таблица `skill_checkpoints` с полями: domain, checkpoint_path, performance, size.
- **API:**
  - `GET /skills` — список доступных скиллов.
  - `POST /skills/request` — агент запрашивает скилл для своего домена; Beacon выдаёт соответствующий чекпоинт.

### 2.4. Протокол обмена весами

**Задача:** Определить формат и API для обмена весами между Beacon и мобильными нодами.

**Формат данных:**
- `WorldModelChunk` уже определён в ТЗ (с полями encoder_weights, predictor_weights).
- Для передачи скиллов: `SkillPackage` (чекпоинт + метаданные: домен, версия, размер).

**API:**
- `POST /weights/upload` — нода отправляет чанк.
- `GET /weights/global` — нода получает глобальные веса.
- `GET /skills` — список скиллов.
- `POST /skills/request` — запрос скилла.

## 3. Что разрабатывается на мобильных нодах (Недели 5–10 MVP)

### 3.1. Экспорт le-wm в ONNX

**Задача:** Конвертировать PyTorch-модель le-wm (ViT-S) в формат ONNX для инференса на мобильном устройстве.

**Шаги:**

1. Загрузить предобученные веса ViT-S из репозитория le-wm.
2. Определить точку входа: энкодер `enc(x) -> z` и предиктор `pred(z, a) -> z_next`.
3. Экспортировать через `torch.onnx.export()`.
4. Проверить результат на тестовых данных, сравнить с PyTorch-выводом.
5. Сохранить `.onnx` файл (размер ~15–30 МБ).

**Риски:** Некоторые операции могут не поддерживаться ONNX; может потребоваться замена на эквивалентные. Решается использованием ONNX opset 17+ и тестированием.

### 3.2. Инференс LeWM на мобильном устройстве

**Задача:** Встроить ONNX-модель в мобильное приложение (Rust, `ort` крейт).

**Компоненты:**
- `LewmRuntime` — обёртка над `ort::Session`. Методы:
  - `encode(image) -> Vec<f32>` (латент размерности 1280).
  - `predict(z, action) -> Vec<f32>` (предсказанный латент).
- Загрузка модели при старте агента (из `assets/lewm.onnx`).
- Инференс на CPU (ORT оптимизирован под ARM).

**Производительность:**
- Целевая скорость: 5–10 FPS для энкодера на кадрах 224×224.
- Потребление памяти: ~50 МБ для модели + ~50 МБ для SDM.

### 3.3. Prediction Head для Bongard+

**Задача:** Создать специализированный модуль, который на основе предсказанного латента оценивает правдоподобность действия (для L1).

**Реализация:**
- Bongard+ уже определён в L1: вычисляется `L_pred = MSE(z_pred, z_actual)`.
- `PredictionHead` — это просто вызов `LewmRuntime::predict()` и расчёт MSE.
- Если `L_pred < τ` (адаптивный порог), действие считается верифицированным.

**Доработка:** В будущем можно заменить MSE на более информативную метрику (Mahalanobis distance), но для MVP достаточно MSE.

### 3.4. MCP-мост для мультимодальности

**Задача:** Агент должен воспринимать не только изображения, но и звук, текст. Для этого нужен MCP-инструмент, который собирает данные с разных сенсоров и подаёт их в LeWM.

**Текущее состояние:** le-wm работает только с изображениями. Для MVP это допустимо — мы начинаем с визуального распознавания.

**План на MVP:**
- Реализовать `camera_capture` как MCP-инструмент.
- Для звука и текста пока использовать отдельные инструменты (`audio_record`, `llm_query`), но не подавать их в LeWM (они работают параллельно).
- В v3.1+ добавить аудио-энкодер (wav2vec2) и кросс-модальный attention.

### 3.5. Лёгкое дообучение на ноде (Federator)

**Задача:** Агент должен не только использовать LeWM, но и локально дообучать её веса (L2).

**Реализация:**
- Federator (уже определён в L2) обновляет веса SDM, но не LeWM напрямую (модель слишком велика для обучения на телефоне).
- В MVP агент отправляет градиенты (или чанки весов) на Beacon, где происходит реальное обучение.
- В v3.1+ можно добавить lightweight fine-tuning (LoRA) для LeWM на устройстве.

## 5. Ключевые риски и их mitigation

| Риск | Вероятность | Решение |
| :--- | :--- | :--- |
| Экспорт le-wm в ONNX несовместим | Средняя | Использовать `candle` (Rust-фреймворк) для прямого инференса без ONNX. |
| ViT-S слишком медленный на CPU | Низкая | Оптимизация через квантование INT8, обрезку модели. |
| Мультимодальность требует переделки архитектуры | Высокая | В MVP работаем только с изображениями; аудио/текст — отдельные инструменты. |
| Beacon не справляется с нагрузкой (1000 нод) | Средняя | Кэширование весов, асинхронная обработка, шардирование. |

## 6. Заключение

Настоящий план детализирует, как именно le-wm интегрируется в WATERS: Beacon становится «заводом» по производству и улучшению моделей мира, а мобильные ноды — их потребителями и поставщиками данных. Первым строится Beacon (1–8 недели), затем мобильная нода подключается к готовому API (5–10 недели). Ключевые доработки — экспорт в ONNX, Prediction Head для Bongard+, и MCP-мост для камеры — выполняются на этапе мобильной разработки. Конструктор может немедленно начинать с развёртывания Beacon и загрузки первой мастер-модели.
